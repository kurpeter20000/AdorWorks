**2026-09-14 — RLS drift found and repaired: 12 policies across 8 migrations were tracked as applied but never actually took effect on staging**
Owner: Claude Code. Found while re-verifying Stage 8's own known gap (the employer applicant-pipeline count against real staff_assisted/self_service data — see that stage's doc). Seeding real data and reading the pipeline count *as the employer* (not the admin client) came back 3 instead of the expected 4: a self-service opportunity's `submitted` application, which migration `0046`'s `applications_select` policy is explicitly written to make visible to the employer, wasn't visible at all.

Direct inspection of the live database's actual RLS policy text (via a raw Postgres connection, `pg_policies`) confirmed `applications_select` was still word-for-word the *original* `0002` version — not `0046`'s — despite `_schema_migrations` recording `0046` (and every migration after it, up through `0069`) as applied. Wrote a script comparing every migration file's *last* intended definition of every policy (148 policy names, parsed from all 70 files) against the live database's actual text: found 12 real mismatches spanning 8 unrelated migrations (`0013`, `0015`, `0020`, `0024`, `0026`, `0039`, `0046`, `0060`) touching `talent_profiles`, `organisations`, `opportunities`, `applications`, `reviews`, `disputes`, and `finance_records`. In every case the *helper functions* these policies were supposed to start using (`is_org_member`, `is_org_write_member`, `is_contract_participant`, `has_applied_to_opportunity`, `has_invitation_for_opportunity`) already existed live and worked correctly elsewhere — only the `DROP POLICY`/`CREATE POLICY` statements themselves never took effect, in every one of these 12 cases specifically. Every case makes the live policy *more* restrictive than intended (a missing OR-branch), not less — a functionality bug (legitimate users wrongly blocked: invited team members, self-service employers, non-representative contract participants), not a security exposure.

Most likely root cause: the earlier 2026-09-14 test-project tracking-table-wipe incident's reconciliation (see that entry above) verified "the actual schema was intact through migration 0060" by spot-checking specific tables/indexes/functions — not by diffing every individual policy's exact text — and missed that these 12 policies were frozen at a pre-restore snapshot while everything else, including the newer helper functions, was already caught up.

Fixed with a new migration, `0070_rls_drift_repair.sql`, re-applying each of the 12 policies' true final text verbatim from its real source-of-truth file — plain idempotent `drop policy if exists / create policy` pairs, safe regardless of which were secretly already correct. Verified: re-ran the drift-comparison script post-fix (0 mismatches, down from 12), then re-ran the exact live Stage 8 pipeline test that surfaced this — the dashboard now correctly shows 4. Full platform test suite (59 unit + 17 e2e) and backend suite (38) all still green after the change.

**This is a staging/test-project-only finding.** Production's migration history runs through the normal CI pipeline and was never touched by the tracking-table incident this traces back to — but the founder should independently confirm production's live policy text actually matches these same 8 migration files before assuming it's unaffected, since the drift was only discoverable by direct database inspection, not by anything `_schema_migrations` or the app's own behavior would have surfaced on its own.

**2026-09-13 — S05-13 live mobile testing caught a real pre-existing overflow bug, misdiagnosed once before being fixed**
Owner: Claude Code. A new Playwright test (`e2e/mobile-responsive.spec.ts`) checking real horizontal overflow at a 360px viewport failed on `/passport` — the *entire* authenticated app shell (header, sidebar wrapper, main content) rendered 24px wider than the viewport, not just passport-specific content, meaning every page sharing that shell was affected. First hypothesis (missing `min-w-0` on the new work-experience date-range flex row) was applied but verifiably did not fix it — re-running the identical failing test showed the identical 24px figure. Root cause, found via direct live DOM inspection against the running dev server: two native `<input type="date">` elements sitting side by side in `WorkExperienceManager` each have a ~140px floor Chromium refuses to shrink below regardless of flex/`min-w-0` overrides on their wrappers, because that floor belongs to the native control itself, not the CSS box around it — combined, the two independently forced the whole page's intrinsic minimum width past 360px. Fixed by stacking the two fields vertically below the `sm` breakpoint instead of forcing them side by side on narrow screens; verified live (all 4 tests pass, `docScrollWidth === innerWidth` exactly). Recorded because the misdiagnosis pattern (a plausible-looking flex fix that doesn't actually address a native-control floor) is a real trap worth remembering, and because it demonstrates why S05-13 needed genuine browser testing — this would not have been caught by code review alone.

**2026-09-13 — Stage 3 complete: S03-10 restore rehearsal verified live, all 12 steps done**
Owner: Founder / Claude Code. Reason: closing out the last open Stage 3 item. The restore-rehearsal workflow took five rounds of real, live-only-discoverable fixes before succeeding (full detail in `docs/governance/backups-and-restore.md`) — each attempt hit a genuine Supabase-specific issue no amount of code review would have caught upfront: restoring a full pg_dump collides with Supabase's own platform-managed schemas (auth/storage/extensions); even scoped to `public`, pg_dump still carries database-wide event triggers owned by a superuser Supabase never grants; `pg_restore --disable-triggers` itself needs superuser for the same reason; and this schema's own business-rule guard triggers reject already-valid data during a plain restore. **2026-09-12 — Production backup workflow live: two real bugs found by actually running it**

**2026-09-12 — Corrected the migration-automation approach after finding it broken live**
Owner: Claude Code. Reason: the first version of `apply-migrations.js` re-ran every migration file unconditionally on every invocation, reasoning that each file's own DDL is individually safe to re-apply. That's true per-file but not true of the sequence as a whole — confirmed live: migration 0003 defines a view that 0034 later redefines with a different column set, and Postgres's `CREATE OR REPLACE VIEW` can't drop existing columns, so replaying 0003 after 0034 has run fails outright. Impact: rebuilt using a `_schema_migrations` tracking table so a file is only ever applied once, which is the standard/correct approach and doesn't have this failure mode.

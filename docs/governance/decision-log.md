**2026-09-13 — Stage 3 complete: S03-10 restore rehearsal verified live, all 12 steps done**
Owner: Founder / Claude Code. Reason: closing out the last open Stage 3 item. The restore-rehearsal workflow took five rounds of real, live-only-discoverable fixes before succeeding (full detail in `docs/governance/backups-and-restore.md`) — each attempt hit a genuine Supabase-specific issue no amount of code review would have caught upfront: restoring a full pg_dump collides with Supabase's own platform-managed schemas (auth/storage/extensions); even scoped to `public`, pg_dump still carries database-wide event triggers owned by a superuser Supabase never grants; `pg_restore --disable-triggers` itself needs superuser for the same reason; and this schema's own business-rule guard triggers reject already-valid data during a plain restore. Final design: data-only dumps (schema is already fully reproducible from migrations), foreign keys dropped and recreated around the load, user-defined triggers disabled and re-enabled around the load. Run #10 succeeded completely — foreign keys recreated and validated against the restored data with zero errors, real row counts confirmed. Stage 3 (data, backups and observability) is now fully complete and verified: schema/ownership map, retention policy, index review, destructive-migration policy, complete audit-event coverage, error monitoring (Sentry), uptime monitoring (UptimeRobot), structured logging, automated backups, restore rehearsal, incident-response doc, and rollback rehearsal.

**2026-09-12 — Production backup workflow live: two real bugs found by actually running it**
Owner: Founder / Claude Code. Reason: closing out S03-09. The founder added the `PROD_SUPABASE_DB_URL` secret and triggered the workflow — it failed twice, each time for a genuine reason only visible from a real run, not something code review would have caught: (1) Supabase's "Direct connection" string resolves IPv6-only, and GitHub Actions runners have no IPv6 route, so `pg_dump` failed instantly with "Network is unreachable" — fixed by switching to Supabase's **Session pooler** connection string instead (IPv4-compatible; Transaction pooler wouldn't work here since `pg_dump` needs session-level behavior transaction-mode pooling breaks). (2) Once reachable, `pg_dump` refused to run at all: Ubuntu's `postgresql-client` apt package installs v16, but Supabase's server is 17.6, and `pg_dump` hard-refuses to dump from a server newer than itself — fixed by running the job inside the official `postgres:17` Docker image instead. Third attempt (run #3) succeeded: produced a real, validated 97KB backup, confirmed via the run's artifacts API. S03-09 is now genuinely complete, not just "code merged." S03-10 (restore rehearsal) is next, now that a real backup exists to restore from.

**2026-09-12 — Corrected the migration-automation approach after finding it broken live**
Owner: Claude Code. Reason: the first version of `apply-migrations.js` re-ran every migration file unconditionally on every invocation, reasoning that each file's own DDL is individually safe to re-apply. That's true per-file but not true of the sequence as a whole — confirmed live: migration 0003 defines a view that 0034 later redefines with a different column set, and Postgres's `CREATE OR REPLACE VIEW` can't drop existing columns, so replaying 0003 after 0034 has run fails outright. Impact: rebuilt using a `_schema_migrations` tracking table so a file is only ever applied once, which is the standard/correct approach and doesn't have this failure mode. Verified both code paths (nothing pending, and exactly-one-thing pending) directly against the live test project before considering this done.
